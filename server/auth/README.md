# Login service (`server/auth/`)

The sign-in page of the public host, in place of the browser's basic-auth prompt. Node, no dependencies.
Caddy asks it about every request on the public listener (`forward_auth`). The open LAN listener and the
secret stream path for external players (`/t/<token>/`) don't use it.

## How a request goes

| request | answer |
|---|---|
| has a valid session cookie | passes (200), and the session's idle clock restarts |
| a page load without one | 302 to `/login?next=<where it was going>` |
| anything else without one (XHR, a segment, a stream) | 401, without `WWW-Authenticate` (that header would bring back the browser's prompt) |
| still has the **old basic-auth password** (a browser that signed in before this service) | requests pass. The next page load goes through `/auth/upgrade`, which gives the browser a session and sends it straight back. People already signed in never see the login page |

`/login`, `/auth/login` and `/auth/upgrade` are the only paths Caddy lets through without a session.

## Security

- **One shared password**, the `password=` line of the host's credentials file (20 random characters,
  generated by the host's setup script). It is read when needed, so a new one counts at once. Comparisons
  are constant-time (`crypto.timingSafeEqual` on SHA-256 digests).
- **Sessions:** a random 256-bit token in a cookie, `__Host-ruby_session`. The cookie is `HttpOnly`, `Secure`
  and `SameSite=Lax`, and its `__Host-` prefix means only this host, over https, can set it. The server
  stores only the token's SHA-256 (`sessions.json`), with when, from where and the browser it came from.
  A session ends after **90 days without use**. Each use restarts that clock, at most once a minute, and the
  `seen` times reach disk every 5 minutes. **Changing the password signs every device out**: a session
  remembers a hash of the password it was made with.
- **Bans per address.** 5 wrong passwords within 15 minutes ban the address: for 1 hour the first time, a
  day the second, 7 days from the third on. After 30 days without a ban the count starts over. IPv6
  addresses are banned per /64, the block one home or server gets. A banned address can't sign in, not even
  with the right password, by form or through the old basic auth. Its existing sessions keep working: a
  cookie can't be guessed, so blocking it would only lock out the people who live there. Bans survive
  restarts (`bans.json`).
- **Many addresses at once:** 100 wrong passwords within an hour, from anywhere, close sign-in for an hour.
  Signed-in devices keep working.
- **The real address** comes from `CF-Connecting-IP`. Only Cloudflare reaches the public listener
  (cloudflared on loopback), and Cloudflare replaces any `CF-Connecting-IP` a visitor sends.
  `AUTH_TRUST_CF=0` for a setup without Cloudflare in front.
- **The old basic auth** counts like the form: a wrong password is a wrong password. A browser keeps
  sending its saved one, and after a password change that one is stale. Each distinct wrong value counts
  once per address, so a stale one doesn't ban its owner, while guessing (a new value each time) is
  counted and banned like the form.
- **The form:** a post from another site is refused (`Sec-Fetch-Site`, or `Origin` in older browsers),
  so another site can't sign a browser in to its own session. `next` is a path on this site only. A wrong
  password waits 1 s before the answer. The page loads nothing from anywhere and runs no script. Its CSP
  allows only its own style (`default-src 'none'`, a nonce), and `frame-ancestors 'none'` keeps it out of
  frames. It is never cached.
- **Journal:** every sign-in, wrong password, ban and closing goes to `journal/<day>.jsonl` (address,
  country, browser), kept 90 days.
- **Telegram** (optional, `AUTH_TELEGRAM`: a JSON file with `token` and `chat_id`): a message for every
  ban, every closing and every sign-in. Each device that moves over from basic auth sends one as well.

## Run

```
AUTH_PORT=8088 AUTH_DATA=<dir> AUTH_CREDENTIALS=<credentials.txt> AUTH_BRAND=Ruby \
  [AUTH_TELEGRAM=<telegram.json>] [AUTH_INSECURE=1] node server.js
```

`AUTH_INSECURE=1` is for testing over plain http: the cookie is named `ruby_session` and isn't `Secure`.

Caddy, on the listener the tunnel reaches:

```
@login path /login /auth/login /auth/upgrade
handle @login {
	reverse_proxy 127.0.0.1:8088
}
handle {
	forward_auth 127.0.0.1:8088 {
		uri /auth/check
	}
	# ... the site's routes
}
```

## Tested (2026-10-20, Mac, Caddy 2.11.7, Chrome in the app's browser pane)

- **The routes, with curl through Caddy:**
  - a page load goes to `/login?next=…` and a fetch gets 401;
  - a wrong password comes back as `e=wrong`, and a cross-site post gets 403;
  - `next=//evil.com` goes to `/`;
  - the fifth wrong password from one address bans it. The right password then gets `e=ban` too, and so
    does a correct basic-auth header;
  - a stale basic-auth password sent 7 times counts once.
- **In the browser:** the page, a wrong password ("Wrong password."), then the right one, then Lampa's
  home. Of 217 requests none was refused (the three 404s are files the dev copy doesn't have), and a
  TorrServer stream answered 206 with the cookie. Page scripts can't see the cookie (`document.cookie`).
- **Moving over from basic auth:** Caddy with `basic_auth`, a tab signed in, then Caddy reloaded with this
  service. The open tab's requests still worked, and the next page load went through `/auth/upgrade` to
  the app without the login page (journal: `"how":"basic"`).
- **Cost:** `/auth/check` with a session took 0.16 ms (median) and 1.0 ms (p99) over 500 requests.
- **Not tested in Safari:** safaridriver needs Safari's "Allow remote automation", which was off.
